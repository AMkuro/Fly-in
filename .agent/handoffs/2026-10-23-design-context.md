## 0. この文書の目的と扱い

本書は、Fly-inの実装前に行ったアルゴリズム、シミュレーションモデル、データ表現、AI開発体制についての議論を記録する。

後続のAIエージェントや人間が、過去の会話を読まずに、以下を理解できることを目的とする。

- 何を目的として設計しているか
- どの選択肢を検討したか
- 何を採用・確認したか
- どの設計が未承認なのか
- なぜ判断を保留したのか
- 次の議論で何を決める必要があるか

本書はFly-in Subjectの代替ではない。Subjectは別途提供される正本とする。

また、本書はコードの現在の実装状況を証明する資料ではない。作業開始時には、エージェントがローカルリポジトリを直接調査すること。

### 0.1 判断ステータス

| ステータス | 意味 |
|---|---|
| `ACCEPTED` | 開発者が明示的に採用した判断 |
| `CONFIRMED` | 外部への確認によって解釈が確定した事項 |
| `PROPOSED` | 検討中の案。採用には承認が必要 |
| `OPEN` | まだ設計・検証・判断が必要 |
| `REJECTED` | 検討した結果、採用しないと判断された案 |

`PROPOSED`や`OPEN`をエージェントが独断で`ACCEPTED`へ変更してはならない。

この文書は作成日時点の記録として保持する。後続の議論で判断が変わった場合、承認された新しい決定を正式な設計文書に記録し、必要に応じて本書から参照できるようにする。

## 1. 開発の基本方針

### 1.1 何を最適化したいのか

**ステータス: ACCEPTED**

Fly-inで重視するのは、理論上の最適解だけではない。

次の複数の要素を総合的に考慮する。

1. Subjectへの適合性
2. シミュレーション完了ターン数
3. アルゴリズムの計算時間・メモリ使用量
4. 実装量・デバッグの難易度
5. 開発者自身の理解・説明可能性
6. 限られた期間に完成させられる確実性

設計議論時点で、提出までの実作業期間は約5日と見積もられている。

計算量が漸近的に優れていても、実装が複雑で検証が困難なアルゴリズムは、今回の開発に適しているとは限らない。

反対に、厳密な最適性を保証できなくても、十分に良い結果を短期間で実装・検証できる方式には採用価値がある。

### 1.2 AIとの役割分担

**ステータス: ACCEPTED**

AIエージェントは実装作業を担当してよい。

ただし、設計判断とその採否については人間が最終責任を持つ。

AIには設計改善の提案を積極的に求めるが、提案を実装に反映する際は人間の承認を必要とする。

特に、新しいクラス、データ形式、アルゴリズム、責務分割、永続的な設定変更を導入する場合、少なくとも次を明確にする。

- 必要性
- 責務
- 入力・出力
- データ型
- 不変条件
- 計算量・実装負荷
- エラー・境界条件
- テスト方法
- 既存設計への影響

実装の詳細をすべて人間が記述する必要はないが、AIがどのような仕組みを実装しているのか理解できるようにする。

既存実装や一般的なアルゴリズムを調べ、根拠のある設計を選択する。

## 2. このセッションで確定した設計判断

### DEC-001: ゴール到着後の状態表現

**ステータス: ACCEPTED**

ドローンがendへ到着した場合、`Delivered`などの専用状態に変更するのではなく、`AtZone(goal)`で表現する。

ここで`goal`はendとして定義されたZoneを意味する。

到着済みかどうかは、状態がendを指していることで判定する。

到着したドローンは以後移動させない。

この方針では、ゴール上に到着した機体も状態データとして保持できるため、到着数の集計や表示に利用できる。

ただし、`AtZone`の具体的なPythonクラス定義、格納方法、履歴との関係は未承認。

### DEC-002: Connection容量についての確認結果

**ステータス: CONFIRMED**

Subjectを読んで生じた疑問について、仲間に確認した結果、以下の2点を採用することになった。

**確認事項1：Connectionの占有判定**

Connection上の占有は、Zoneと同様にターン終了時の状態を基準としてよい。

**確認事項2：双方向容量**

Connection容量は双方向の移動で共有する。

A→BとB→Aは、別々の容量を持つわけではない。

ただし、この2点だけでConnection利用の全ケースについて、正しい容量計算式が決まるわけではない。

具体的な計算式は「OPEN-001」に記録する。

### DEC-003: 既存データ形式を固定しない

**ステータス: ACCEPTED**

既存のデータモデルや実装は尊重する。

ただし、後続のアルゴリズムにとって利用しにくい、処理が煩雑になる、データの不整合を招く、性能に問題がある、といった理由が確認された場合には改善する。

例えば、内部データのキーを文字列にするか整数IDにするか、隣接リストを使うか行列を使うかなどは、既存コードだけを根拠に決めない。

変更には説明と承認が必要だが、既存形式を維持すること自体は目的としない。

### DEC-004: AIの作業をトピック単位に分離する

**ステータス: ACCEPTED**

GUI、アルゴリズム、シミュレーション、テスト、CIなどを、一つの長いAIセッションで同時に議論し続けない。

対象を分離し、それぞれについて独立して議論・設計・実装・レビューできるようにする。

各トピックには、関連するGitHub Issueと必要な設計文書を対応させる構想。

議論が終了した際には、重要な決定と未解決事項をGitHub上に残す。

## 3. 状態・行動・移動計画の考え方

### 3.1 状態と移動を区別する

**ステータス: PROPOSED**

ある時点でドローンがどこに存在するかという情報と、状態を変化させる操作を区別する。

概念上は次の3種類の情報を考えている。

| 概念 | 役割 |
|---|---|
| State | あるターン終了時点のドローンの状態 |
| Action / Move | あるターンに実行する行動 |
| Plan | 将来実行する行動の予定 |

この区別は設計上有用だと考えられているが、3種類すべてを独立したPythonオブジェクトとして保存することは決定していない。

### 3.2 検討中のデータ表現

以下は概念的な例であり、実装済みクラスや承認済みの型定義ではない。

```python
TurnState(
    turn=0,
    positions={
        1: AtZone("start"),
        2: AtZone("start"),
    },
)
```

移動中の状態が必要な場合の候補：

```python
InTransit(
    connection="A-R",
    destination="R",
    arrival_turn=3,
)
```

`InTransit`は、ドローンが接続上を移動している状態を表す案。

具体的な状態フィールドやターン番号の付け方は、状態遷移の設計時に確定する。

### 3.3 PlannedMoveは誰が生成するのか

**ステータス: PROPOSED — 概念上の誤解は解消済み**

`PlannedMove`は、移動を計算する主体ではなく、計算された移動を表すデータとして提案された。

例えば、計画を表すデータとして以下を考えられる。

```python
PlannedMove(
    drone_id=1,
    from_zone="A",
    to_zone="B",
    connection="A-B",
    departure_turn=2,
    arrival_turn=2,
)
```

これは、移動を計画する処理が決定した結果を表す例。

初期状態を作る時点で、この移動計画が必ず存在するわけではない。

処理の順序は概念的に次のようになる。

1. 入力マップとドローンの初期状態が用意される。
2. Plannerが移動を計算する。
3. Plannerが移動計画を生成する。
4. Simulatorなどが計画に基づいて状態を更新する。

ただし、具体的な`PlannedMove`のフィールド、ターン番号の定義、複数移動の保持方法は未承認。

### 3.4 PlannerとSchedulerの責務

**ステータス: OPEN**

暫定的には次の区別が考えられる。

- `PlannedMove`：移動内容を表すデータ
- `Planner`：経路や移動時刻を計算する処理
- `Scheduler`：複数ドローンの計画・競合・予約を調整する処理

ただし、PlannerとSchedulerを独立クラスにすべきかは決定していない。

両者の処理が密接であれば、統合した方が責務が明確になる可能性もある。

**クラス数を増やすことより、機能の境界が明確であることを重視する。**

### 3.5 データの正本

**ステータス: OPEN**

State、Move、Plan、Reservation、Snapshotなどの情報を、すべて別々に保存する必要があるかは未決定。

例えば、Planを正本にしてSnapshotを生成する方法もある。

逆に、シミュレーションの各ターンの状態を記録して、そこから出力やGUIを生成する方法もある。

同じ情報を複数箇所に保存する場合は、整合性を保つ責任と更新処理が必要になる。

どのデータを正本とするかは、アルゴリズムとGUI連携を考慮して決める。

## 4. 保留中の重要な問題

### OPEN-001: Connection容量の計算方法

**ステータス: OPEN — 明示的に保留**

Connectionの占有状態と、Connectionを使用した移動をどのように数えるかが未解決。

問題の例を示す。

容量1のConnection A-Bがあるとする。

ターン開始時、D1とD2がAにいる。Bには2機を受け入れられる余裕がある。

同じターンに両機体がAからBに移動した場合、ターン終了時には2機ともBに存在し、Connection上には存在しない。

したがって、**Connectionのターン終了時の占有数だけでは、同一ターンに2機がConnectionを通ったことを検出できない。**

別の例として、D1がAからBへ、D2がBからAへ同時に移動する場合も考えられる。

ターン終了時のZone占有数が変わらなくても、Connectionを双方向で利用している。

そこで、次の量を導入する案が議論された。

- ターン終了時のConnection占有数
- そのターンのConnection通過・利用数

検討された暫定案の一つは、

\[
U_e(t)=N_{\mathrm{transit},e}(t)
+N_{\mathrm{normal\_move},e}(t)
\]

として、

\[
U_e(t)\le \operatorname{capacity}(e)
\]

を判定するというもの。

ここで、

- \(N_{\mathrm{transit},e}(t)\)：ターン終了時にConnection上にいる機体数
- \(N_{\mathrm{normal\_move},e}(t)\)：同じターンに通常移動でConnectionを通過した機体数

を意味する。

**この計算式は未承認であり、採用してはならない。**

とくに移動中の機体がConnectionから出るターンに、他の機体が同じConnectionを利用する場合の取り扱いを、すべて検証できていない。

今後は、具体的な状態遷移の組合せを整理し、容量判定の正当性を検討する必要がある。

この論点が未解決の間、エージェントは暫定式を確定仕様として実装してはならない。

### OPEN-002: 状態遷移処理の契約

**ステータス: OPEN**

状態遷移には少なくとも次の情報が必要と考えている。

入力候補：

- 現在の状態
- 次ターンの行動集合
- グラフ・移動規則

出力候補：

- 次の状態
- 行動の結果
- 違反がある場合のエラー情報

ただし、入力型・出力型・エラー表現、純粋関数的な設計にするか状態を変更するかなどは未決定。

### OPEN-003: IDと内部表現

**ステータス: OPEN**

ドローン、Zone、Connectionは安定した識別子で扱うことを検討している。

特に、同一Connectionを両方向から利用しても、同じConnectionを参照できる必要がある。

ただし、内部IDを文字列にするか整数にするか、外部名との対応をどこで保持するかは未承認。

データ構造は、検索効率・更新負荷・実装の単純さを比較して選定する。

## 5. アルゴリズムの検討結果

### 5.1 問題の分類と具体的な解法を区別する

**議論で得た理解**

「最大フロー」「最小費用最大フロー」は、具体的な単一アルゴリズムの名称ではなく、最適化問題の分類。

それに対して、Ford–Fulkerson、Edmonds–Karp、Dinicなどは最大フロー問題を解く具体的なアルゴリズムである。

同様に、Dijkstra、Bellman–Ford、A*は最短経路探索に利用する具体的な方法。

そのため、「最大フローを利用する」と言っても、実際のグラフの定式化方法と使用するアルゴリズムをさらに決める必要がある。

### 5.2 検討したアルゴリズム

| 手法 | 議論で得た結論 |
|---|---|
| Dijkstra | 非負の移動コストを持つ経路探索に適用可能 |
| Bellman–Ford | 負の辺を扱えるが、今回の通常の経路探索では積極的な採用理由がない |
| A* | 適切なヒューリスティックにより探索を効率化できる可能性がある |
| Kruskal | 最小全域木を求める手法で、目的が異なる |
| BFS | 全遷移を1ターン単位にすれば、最短到着時刻を探索できる |
| 最大フロー | 複数機体をまとめて扱える可能性があるが、完全なモデル化は未検証 |
| 最小費用最大フロー | 総費用の最小化と最終到着ターンの最小化は同じとは限らない |
| CBS | 複数エージェント経路探索の候補。ただし今回の制約への対応が必要 |

### 5.3 A*のヒューリスティック案

**ステータス: PROPOSED**

単なる座標上の距離より、グラフ構造に基づいたヒューリスティックが適切ではないかと議論した。

候補は次の2つ。

1. ゴールまでの最小ホップ数
2. 混雑を無視したゴールまでの最短移動時間

2番目は、グラフの移動コストに応じてDijkstraなどで計算できる。

共通のゴールを持つ場合、ゴールから逆向きに探索して各Zoneまでの残りコストの下界を事前計算する案がある。

移動先に応じてコストが決まる場合、逆方向の探索で使用する重みも適切に設定する必要がある。

A*で最適性を保証するためには、ヒューリスティックが真の残りコストを過大評価しないことが重要。

動的な混雑を適当に加点するだけでは、その保証が失われる可能性がある。

### 5.4 なぜBFSが候補になったのか

**議論で得た理解**

状態を1ターンごとに展開し、探索グラフの1辺が必ず1ターンに対応するなら、すべての探索辺のコストを1として扱える。

この場合、BFSでも最短到着時刻を探索できる。

Dijkstraを使っても同じ最短到着時刻を求められるが、重みがすべて1ならBFSの方が単純。

ただし、BFSがA*より常に高速という結論ではない。

探索空間とヒューリスティック次第ではA*の方が少ない状態数で探索できる。

**BFSの採用は未決定。**

### 5.5 比較した3つの設計方式

#### 方式A：全体状態探索

すべてのドローンの状態の組合せを1つの探索状態として扱う。

適切なBFSやA*を使えば、正確な状態遷移モデルの下で全体最適解を探索できる。

ただし、ドローン数が増えると探索状態が急増する可能性がある。

#### 方式B：時間展開ネットワーク＋最大フロー

時間ごとのZoneやConnectionをグラフ上に表現し、整数フローをドローンの輸送に対応させる。

一定の時間内に必要なフローを流せるかを判定し、最小完了時間を探索するという考え方。

単純なグラフのサイズはターン数に比例して増やせるが、容量共有、方向、移動時間を正確に表現する必要がある。

**合法なスケジュールと整数フローが一対一に対応することは、Fly-inに対してまだ証明していない。**

このため、方式Bは有望だが、実装可能性と正当性の検討が必要。

#### 方式C：時間付き予約管理＋BFS/A*

ドローンごとに、他機体が使用する予定のZone・Connectionを考慮して経路探索する。

経路を決定したら、使用時刻とリソースを予約する。

基準実装として比較的取り組みやすいと提案された。

ただし、先に確定した経路が後続機体を妨げる可能性があり、全機体の完了ターン数について最適性は保証されない。

### 5.6 現在の選定状況

**ステータス: OPEN**

正式な採用アルゴリズムは決まっていない。

方式Cを、開発期間と実装難易度の観点から基準候補として提案した。

方式Bも比較対象として残している。

方式Aについては、計算量・探索空間の大きさに懸念がある。

重要な点として、方式Cを段階的に拡張するだけで方式Bになるわけではない。

両者は共通のモデル・出力・テストを利用できる可能性があるが、アルゴリズムそのものは異なる。

今後の検討では、理論上の最適性だけでなく、実装量、検証容易性、配布マップでの性能を比較する。

### 5.7 最短完了ターンの下界

**ステータス: 検討済みの数学的性質**

次の下界を議論した。

\[
T_{\min}\ge L+\left\lceil\frac KC\right\rceil-1
\]

ここで、

- \(T_{\min}\)：最短完了ターン数
- \(L\)：混雑を無視した共通始点から共通終点までの最短移動時間
- \(K\)：ドローン数
- \(C\)：1ターン当たりの始点からの初回出発可能数の上限

成立条件は、すべての機体が共通始点から出発し、各機体の到着までに最低\(L\)ターン必要で、1ターンの初回出発数が最大\(C\)であること。

最後に初回出発する機体は、早くても

\[
\left\lceil\frac KC\right\rceil
\]

ターン目に出発する。

その機体が到着するまで、さらに最低\(L-1\)ターン必要なので上式が得られる。

\(C>0\)かつ有限の経路が存在することを前提とする。

この式は特定の論文から引用したものではなく、出発容量と移動時間からこのセッションで導出したもの。

**下界は達成可能性を保証しない。**

性能測定時に、得られたスケジュールと理論下界を比較するために使える。

## 6. インターフェース設計の検討

**ステータス: PROPOSED — 入出力の方向性は概ね了解済み**

以下は詳細設計の出発点であり、採用済みのクラス構成ではない。

| 処理 | 入力候補 | 出力候補 |
|---|---|---|
| 状態遷移 | 現在の状態、次ターンの行動集合、グラフ | 次状態、または制約違反 |
| 経路探索 | グラフ、出発状態・時刻、予約 | 時刻付き経路、または探索失敗 |
| 予約確定 | 時刻付き経路 | 更新済み予約情報 |
| 全体計画 | グラフ、ドローン数 | 全機体の計画 |
| Snapshot生成 | 状態履歴または計画 | ターン別の表示用状態 |
| 出力変換 | ターン別の行動 | CLI向け出力 |

既存のParser、Graph Model、GUI等との具体的な接続方法は、リポジトリの実装を確認した後で決める。

責務を分離することは重要だが、同じ判定ロジックを複数クラスで重複実装しない。

また、GUIが探索アルゴリズムの内部データ構造に強く依存しない設計を検討している。

## 7. GitHubによる開発管理構想

### 7.1 目的

**ステータス: ACCEPTED — 開発方針**

一つの長い会話に、GUI、アルゴリズム、状態モデル、CIなどを混在させない。

GitHub Issuesを議論・作業単位に、GitHub Projectsを進捗・依存関係の管理に利用する構想。

各Issueでは、人間とAIが設計について議論し、合意した内容を実装・検証へ進めたい。

GitHub Issue上でAIと直接対話する方法にも関心がある。

PR上のCodexレビューやAIへの追加指示と同様に、Issueを起点に対話し、議論結果を記録できる仕組みを望んでいる。

ただし、利用するAI製品、Issueコメント上の対話可否、記録方法、必要な権限については正式に選定していない。

### 7.2 IssuesとProjectsの役割

**ステータス: PROPOSED**

GitHub Issue：

- 独立した設計・実装トピック
- 作業の目的と範囲
- 未決定事項
- 議論の履歴
- 受け入れ条件
- 関連する決定文書・PR

GitHub Projects：

- 進捗
- 優先度
- 作業の分類
- 依存関係の可視化
- 作業全体の把握

依存関係はGitHubの既存機能を優先して利用する。

詳細なProjectフィールド、Issue分割方針、承認ステータスの表現は未承認。

### 7.3 タスクを分割する基準

**ステータス: PROPOSED**

Issueは単なるファイル単位ではなく、独立した議論・実装・検証が可能な作業単位とする。

分割時には次を考慮する。

- 作業の目的が明確か
- 入力・出力や受け入れ条件を定義できるか
- 必須の依存関係が明確か
- 他Issueとの責務重複がないか
- 作業量が過大・過小でないか
- 人間による設計承認が必要な範囲を特定できるか

既存実装がある領域では、新規実装だけでなく、調査、修正、結合、テストをタスクとして扱う。

依存関係の網羅性はまだ検証していない。

## 8. リポジトリ内の文書とAgent指示

### 8.1 希望する構成

**ステータス: ACCEPTED — 構想上の基本方針**

リポジトリに次を設けたい。

**`.agent/`**

AIエージェント向けのMarkdown、作業ルール、セッション引き継ぎ情報を保持する。

**`docs/`**

人間とAIが参照する、承認済みの設計文書、意思決定記録、開発運用情報を保持する。

ただし、具体的なディレクトリ階層とファイル名は未承認。

### 8.2 情報の正本と同期

**ステータス: PROPOSED**

同じ情報をIssueとMarkdownに全文コピーして二重管理しない。

想定する役割：

| 情報 | 管理場所 |
|---|---|
| AIへの作業指示 | `.agent/` |
| セッション引き継ぎ | `.agent/handoffs/` |
| 確定した設計とその根拠 | `docs/decisions/` |
| 現在の実装アーキテクチャ | `docs/architecture/` |
| 開発運用のルール | `docs/workflow/` |
| 議論と作業履歴 | GitHub Issues |
| タスクの進捗 | GitHub Projects |

Issueで設計判断が確定した場合、承認済みの内容を`docs/`に反映し、Issueから該当文書へリンクする方式を検討する。

ただし、同期をどのタイミングで誰が行うか、自動化するかは未決定。

初期段階では手動またはAgentによる更新と人間のレビューで十分な可能性がある。

### 8.3 Agentの自動読み込み

**ステータス: PROPOSED**

AI向けの文書は原則として`.agent/`にまとめる。

一方、利用するエージェントが特定の名前・配置の指示ファイルを自動認識する場合には、その要件に従う。

例えばCodexでは、ルートの`AGENTS.md`を短い入口として設け、詳細を`.agent/`に置く案がある。

この構成は正式には未承認。

### 8.4 Skillsとhooks

**ステータス: OPEN**

Agent Skills、hooks、独自自動化は必要に応じて検討する。

最初からすべて導入することは目的ではない。

反復的な開発・レビュー作業を減らす効果、設定の保守負荷、期限への影響を比較して採否を決める。

## 9. ブランチ・CI・提出運用

### 9.1 ブランチ運用

**ステータス: ACCEPTED — 目指す役割分担。移行手順はOPEN**

開発者は次の役割を希望している。

- `develop`：日常開発、設計文書、Agent設定、実験・検証記録を含むブランチ
- `master`：42に提出するためのクリーンな成果物を保持するブランチ

実際の42への提出は、42イントラのGitリポジトリへpushする。

GitHub側の開発リポジトリと、42側の提出リポジトリは区別する。

このため、提出物を選別したブランチをGitHub側に保持し、そこから42側へpushする方式を考えている。

既存ブランチからの移行、提出物の選別方法、GitHubのデフォルトブランチ設定は未決定。

通常のマージだけでは開発用ファイルが提出ブランチに含まれる可能性があるため、提出対象の選別・検証手順を定める必要がある。

### 9.2 CI

**ステータス: ACCEPTED — 段階的導入方針**

CIは最小構成から段階的に導入する。

検討する段階は以下のとおり。

| 段階 | 主な目的 |
|---|---|
| Stage 1 | flake8・mypyなどの静的検査 |
| Stage 2 | 実装済み機能の単体テスト |
| Stage 3 | CLIとシミュレーションの統合テスト |
| Stage 4 | 性能評価・提出用成果物の検証 |

各段階をいつ導入するか、どこまで自動化するかは作業状況を見て判断する。

CIそのものの構築に時間を使いすぎず、Fly-inの正当性と完成を優先する。

### 9.3 テストとシミュレーションの検証

**議論で確認した方針**

シミュレーションの出力を1ターンずつ検証する仕組みは、テストとして用意する方向。

本番実行時に、独立した検証器を毎ターン走らせることは必須ではない。

ただし、経路探索やスケジューラには、それ自身が合法な行動を選ぶための制約判定が必要になる。

テスト用の検証は、スケジューラと同じ誤りを共有しないように設計することが望ましい。

## 11. 次に行う開発管理上の作業

本書に記録された構想を、実際のリポジトリとGitHub上の管理体系へ落とし込む必要がある。

その際、最初から大規模な変更を行うのではなく、以下の順序を想定する。

1. Agentがローカルリポジトリの現状を調査する。
2. 文書体系とAgent指示体系を提案する。
3. 人間がファイルの役割・配置を承認する。
4. 承認された文書構成を作成する。
5. 実装作業の洗い出しと依存関係を検証する。
6. GitHub Issues・Projectsの登録構成を承認する。
7. トピック単位で設計・実装・検証を進める。
8. 段階的にCIを構築する。
9. 提出用のクリーンな成果物を検証する。

この順序は初期案であり、作業間の並行実施や統合は、実際の作業量に応じて検討する。

開発期間が短いため、文書や管理機構の完成そのものを目的化しない。

## 12. 後続AIエージェントへの注意事項

この文書には、採用済みの判断と未承認の設計案が混在している。

後続のAIエージェントは、次を守ること。

1. Subjectを正本とし、この文書でSubjectの内容を補完・変更しない。
2. リポジトリの現在の実装状態は、作業開始時に直接確認する。
3. `ACCEPTED`と`PROPOSED`を区別する。
4. `OPEN`の項目を勝手に確定しない。
5. Connection容量の暫定式を承認済みと扱わない。
6. `AtZone(goal)`による到着済み管理は採用済みと扱う。
7. `PlannedMove`は計算結果を表す候補であり、初期状態から存在するデータだと仮定しない。
8. Planner / Schedulerの責務分割を確定事項として扱わない。
9. 予約付きBFS、A*、最大フローのいずれも正式採用済みとは扱わない。
10. 既存データ形式への固定を前提としない。
11. 変更の提案時には、必要性・影響・検証方法を説明する。
12. 人間が承認していない変更を実行しない。

本書は、過去の議論の全文ではなく、次の設計判断に必要な情報を保存した記録である。

今後の正式な決定は、GitHub Issueと承認済みの設計文書によって管理する。
