# Fly-in decision index

決定の採否・理由・根拠と、関連文書・Issueへの索引。契約本文は[architecture.md](architecture.md)、Agentの行動規則は[AGENTS.md](../AGENTS.md)、運用手順は[development.md](development.md)を正本とする。

初期移行日: 2026-10-24 JST。
[2026-10-23引き継ぎ記録](../.agent/handoffs/2026-10-23-design-context.md)は変更せず履歴として保存する。冒頭の「レビュー・承認前」とは別に、個別の`ACCEPTED`／`CONFIRMED`を維持することは開発者に確認済み。
今回の文書構成・作業規則の承認根拠は、2026-10-24の文書管理構成実装依頼。関連Issue・PRのURLは提供されていないため、架空のリンクは設けない。

`ACCEPTED`は明示的に採用された判断、`CONFIRMED`は外部確認による解釈、`PROPOSED`は未承認案、`OPEN`は未解決、`REJECTED`は不採用を表す。採否と実装の有無は別に管理する。
各決定は安定したIDの節とし、分割が必要になったらIDを維持して個別ファイルへ移し、本索引からリンクする。置換時は旧判断を履歴として残し、後継IDと承認根拠を記録する。索引の自動更新は未導入。

## DEC-004 — 作業をトピック単位に分離する

## DEC-005 — 完成と説明可能性を含めて設計を選ぶ

- 結論・状態: Subject適合性、完了ターン数、計算資源、実装・デバッグ負荷、理解・説明可能性、完成の確実性を総合して選ぶ（`ACCEPTED`）。
- 理由: 理論上の最適性だけでは、限られた開発期間で完成・検証できるとは限らない。高度な手法も説明可能であれば禁止しない。
- 関連文書: [作業規則](../AGENTS.md)。根拠は引き継ぎ記録の1.1と今回の依頼。過去の「約5日」は現在の期限として更新・転用しない。関連Issue: 未確認（URL未提供）。

## DEC-008 — 開発と提出を分離し、提出前に人間が承認する

- 結論・状態: `develop`を開発、`master`を提出成果物のブランチとし、42提出リポジトリも区別する。提出反映前に別途人間のコードレビュー・承認を必要とする（`ACCEPTED`）。
- 理由: 開発用資産と提出成果物を区別し、提出判断を自動検査の成功だけに委ねない。
- 関連文書: [承認規則](../AGENTS.md)、[現行の提出手順](development.md)。段階的にCIを導入する方針も維持するが、現行設定の存在は未決定の解釈を承認しない。
- 根拠: 引き継ぎ記録の9.1・9.2と今回の依頼。2026-10-24の自動同期停止依頼により、CIからの自動反映を廃止。バージョン変更・重要なマイルストーンで、PRによる人間のコードレビューと明示的承認後にリリースする。`main`・`develop`・`master`を維持し、`main`の役割変更は別途判断する。候補作成・リリース機構の構築は後続タスクとする。関連Issue: 未確認（URL未提供）。

## DEC-009 — 重複メタデータを拒否する

- 結論・状態: 同じキーを一つのメタデータブロックに複数回指定した入力を、値が同じ場合もエラーにする（`ACCEPTED`）。
- 理由: これまでの「最初の値だけ採用」では、入力の誤りや競合する指定が黙って隠れる。
- 根拠: 2026-10-25 JSTのT04作業セッションで、開発者が「重複メタデータもエラーにすることを承認する」と明示回答。Subjectの明文とは区別する。
- 関連Issue: [T04 / #4](https://github.com/AMkuro/Fly-in/issues/4)。入力契約は[README](../README.md#map-input)、処理境界は[architecture](architecture.md#implemented)を参照する。自己接続・未知メタデータの既存制約について新たなSubject解釈は確定しない。
